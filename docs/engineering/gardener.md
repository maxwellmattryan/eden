## The key

Keys are T3 and per device (`product/substrate/integrations.md`, "Secrets"): they live in the OS keychain, never in the Vault, which the AI subsystem structurally cannot read, and never in the workspace database. `SecretStore` follows the DB key provider's split by target system:

| platform | store |
|---|---|
| macOS, iOS | the Keychain, service `eden.secrets`, account = the secret's name, this device only, readable after the first unlock. The unsigned development build on macOS uses the file store instead: a rebuilt unsigned binary cannot read what the last one wrote to the Keychain |
| Android | the Keystore through `EdenSecrets.kt`, the same wrapping pattern as the DB key; written and unrun (the checklist in `engineering/data-layer.md`) |
| Windows, Linux | `<app data dir>/secrets/<name>`, mode 0600, until their keychain paths are ported |

The Anthropic key is `anthropic-api-key`. Three commands touch the store (`set_secret`, `has_secret`, `delete_secret`) and none answers a value: the adapter reads it inside the crate, and the webview only ever learns "present" or "absent". A key never appears in an export, a diagnostic, an audit entry or an error message; the adapter strips URLs and headers from a network error before it is emitted.

## The request

The webview builds the whole request and the crate adds only the key. `gardener_send(request, onEvent)` takes `{ id, model, maxTokens, system, messages, tools, outputFormat? }` (`outputFormat` is a JSON schema the reply is held to, sent as the API's `output_config.format`; a delegated request's alone), records the egress (`anthropic`, the URL and the body's bytes; D-71) and POSTs to the Messages API with `stream: true`. The stream comes back over a Tauri channel as events:

| event | carries |
|---|---|
| `start` | the message id and the model that answered |
| `text_delta` | a piece of the reply |
| `tool_use` | one complete tool call: id, wire name, parsed input |
| `thinking` | one whole reasoning block as the provider sent it (`thinking` with its signature, or `redacted_thinking`) |
| `usage` | tokens in, out, cache read and cache written; once at the start, once at the end |
| `stop` | the reason (`end_turn`, `tool_use`, `max_tokens`, `refusal`, `cancelled`) and the refusal's category |
| `error` | the provider's status and message, or a network failure mid-stream |

`gardener_cancel(requestId)` aborts a stream. The adapter never sends `thinking` (the current models decide for themselves) nor `tool_choice` (a forced choice is refused by the current models). A model that reasons returns its reasoning as blocks, and the API wants them back unchanged while a request continues: the runtime keeps each `thinking` event in its place among the reply's blocks and sends it back with the tool results of that request, and keeps it nowhere else (never on the thread row, never in a later request). That reasoning counts toward `max_tokens`, so a model the seed marks `thinks` is given room for it on top: 4096 more for the conversation, 2048 more for a delegated request, and the estimate is made from the same figure. A model the owner adds carries no mark and gets none; a 400 is shown as the provider wrote it, which is how Fable's retention requirement reaches the owner. No key on this device is `gardener:no-key` before anything is sent.

## The loop

One owner message is one request, and one request is one audit entry. In order:

1. No key: the grey chip and the notice. Budget: this month's spend plus the estimate over the cap declines with a link to the Gardener tab (D-7).
2. `resolveGrade` at the conversation's grade (`settings.gardenerGrade`, the chip's switch); unavailable says why; a move above the grade for a need is confirmed with its estimate first (D-74).
3. `buildPack` (below). Over the per-request token cap declines.
4. The owner's message and an empty reply are rows of the thread; the can-see block is written from the pack. The reply carries a `writing` block while its request runs, and the request's audit entry is kept on the device as open (below).
5. The request streams. Text lands in the reply's text block. A `tool_use` runs its handler:
   - a **plain** tool, and a `write-draft` one, runs inline; its card is `running` and settles `done`, and its answer becomes the `tool_result`. A handler that throws, or answers `{ error }`, settles the card `failed` with the error on it, and the model gets the same error result; an answer with `cancelled: true` (a cost declined, the owner's Stop) settles it `cancelled`;
   - a **write** tool asks the grant store (`subject` the model id, `resourceType: 'tool'`); a standing grant runs it with an undo toast; otherwise the tool card waits `pending` with its confirm and the request pauses; confirmed, it is `running`. Confirm records a `per-request` grant (`origin: 'confirm'`; `log-quick` a `standing` one, the Quick Log's first-use pattern) and runs it; cancel answers the model with an error result;
   - an **act-external** tool always takes the confirm path; no Phase 1 tool declares it;
   - a **model-backed** tool is a delegated request: `resolveTool` with the policy's overrides, a confirm when it runs at `deep` or above its declared grade, its own pack from its declared reads alone with the tool's prompt as the message, the files its delegate names (`Delegate.files`, below) and no tools (bounded, never a loop), a system prompt of its own and, where the handler parses JSON, the schema its answer is held to ("A delegated request", below), its own audit entry with `parentRequestId`, and its parsed answer as the `tool_result` and, for `write-draft`, a draft card. Its place in the thread is its tool card alone: the delegated answer is read by the handler and never streamed into the thread, and no holder message is written (the audit entry's `threadId` and `parentRequestId` walk it back to its chat).
6. `stop: tool_use` continues the same request with the assistant's blocks and every tool result, six rounds at most. The sixth round's results go back with a line saying it was the last, and one more request is made for the words that close the reply, so a reply never ends on a tool card; a tool asked for after that is not run. `end_turn` settles. `max_tokens` marks the reply cut short with a Continue. `refusal` shows the category. An error shows the message; a network failure, 429 and 529 offer a retry (below).
7. The `writing` block comes off the reply. The audit entry is written with the usage, the cost from the pricing row, the reads with their row ids, the entities, the tools with their confirm outcome, the grants, and the outcome. The thread's tier rises to the highest tier read. The profile's usage counts are read again. At 80 % of the cap the warning shows once a day.

Draft cards are the runtime's: a task, a plan (tasks and a `shop-day` Event through a batch), a grocery list, code (copied, never written to a file), a capture (stock rows read from the owner's files), a recipe, and the proposal card (`profile.propose`, D-72). A commit is an ordinary store write with an undo toast and a feed entry; the card's state is settled on the message row. A `capture` and a `recipe` draft are not committed in the panel: the card's button hands the draft to its domain's `openDraft` binding (`engineering/domain-module.md`, "Bindings"), which opens it on the domain's own surface, Hearth's capture sheet at its rows or its Recipes pane as an unsaved draft, and the card settles when the owner keeps or discards it there (D-86). A draft is shown as its own message after the reply, the Gardener's bubble in honey (`GardenerMessage` `tone="honey"`) with the draft's title as its header and no access badge. A drafted task becomes a todo due today when the draft names no day, as a line added on Today is, and a time of day is joined into the due.

### A tool run from a page

A page may run a model-backed tool itself, with no conversation (D-86). Hearth's capture sheet and its recipe import are the two that do.

- `runtime.runDirect(toolKey, input, { files, confirmed })` takes `<domain>.<tool>` and runs a `read` or a `write-draft` tool that has a delegate; a write keeps its card and its confirm in a conversation. It is the delegated request of step 5 with no thread: the same resolution, pack, budget check and audit entry, whose surface is `delegated` and which has no thread and no parent, and lists the files under `attachments` by hash, type, size and pixels (D-83). It answers the tool's `ToolResult`.
- `ToolResult.failure` is why nothing was answered, as a code the page puts its own words to: `busy`, `no-key`, `unavailable`, `budget`, `network`, `refusal`, `max-tokens`, `cancelled`, `unreadable`, `empty`, `no-files`. The `output` beside it is still written for the model.
- `confirmed: true` says the page showed the estimate and the owner went ahead, so the cost confirm is not asked again and the entry records it as confirmed. Without it a request that owes a confirm is declined: the confirm sheet is the panel's, and the panel may not be open.
- `runtime.previewDirect(toolKey, input, { files })` answers the provider, the model and the estimate, or why the tool cannot run (`no-key`, `unavailable`, `budget`). It reads no file and sends nothing: the files are counted by their blocks.
- One stream runs at a time. While a direct run is under way `runtime.direct` is true and the panel's send waits; a direct run asked for while a request streams answers `busy`.

### A request that never settled

The provider's stream cannot be resumed, so a request the app closed on (a quit, a crash, a reload of the webview) is lost from where it stopped. Two things keep it from being lost silently:

- **The reply says so.** The `writing` block is on the reply from the moment it is appended and comes off when the request ends, however it ends. A reply that still has it and is not the one the runtime is writing (`runtime.live`) reads as interrupted: the bubble is drawn even when nothing arrived, with what did arrive, its cards read as cancelled, and a notice. This is derived when the thread is read, as a card's state is; nothing is rewritten.
- **The log says so.** `openRequests` (`packages/shared/src/gardener/open-requests.ts`) keeps each request's audit entry in `localStorage` (`eden:gardener-open`) from the moment it is sent, a delegated request's too, with the outcome `interrupted`, the pack's estimated tokens in, and then whatever usage the provider has reported; writing the real entry takes it away. What is still there when the app next starts (`runtime.settleOpen`, once, when the panel first opens and before the first request) is recorded as it stands, so the month's spend counts it. The output tokens of a cut request are the last the provider reported, which may be none.

**Retry** is offered on a reply that was interrupted, or that failed with `network`, 429 or 529, while it is the thread's last message and follows the owner's. It fades the reply, deletes it for good (`delete_message`, a tombstone; no undo), and answers the owner's message anew as a new request with its own entry; the interrupted one keeps its entry. A write the deleted reply had already made stays made, and the new request may make it again.

A request writes to its own reply whichever thread is open: the reply is held by the thread store (`hold`, `release`) while it is written, so opening another conversation or a new one loses nothing, and opening its thread again shows it still being written. One request runs at a time, so the composer is busy in every thread until it ends.

While a reply is awaited the panel shows the kit's `Sprouting` (D-80). Before the reply exists (the pack being built, the budget read) the runtime's `preparing` holds the thread's id, and the panel draws one bubble with the sprout after the thread's last message, unless the cost confirm is up; the same row stays while the reply is live and has no segment, so the sprout never starts over between the two. Once the reply has a segment its own bubble draws the sprout after its cards whenever `awaitsWords` (`packages/shared/src/gardener/segments.ts`) says so: the last segment is not text, no card in it is running or pending, and it is not an error. The browser's scripted transport waits 1.2 s before its first word of each round so the sprout can be seen there.

Handoffs:

- The tools page and the tool popover show a tool's description (`ToolAbout`), which is now written for the model: what comes back, which ids to pass. An owner's line per tool, in the locale files, would read better there.
- The mobile chat (#19) draws from `segmentsOf`, which skips the `writing` block; it needs the same interrupted rule, notice and Retry, and the same sprout: `Sprouting` in a bubble while `preparing` or an empty live reply, and after the cards when `awaitsWords`.
- The sprout does not show while the model writes a tool call after its words: the stream reports a call only once it is whole, so the last segment is still text. A `tool_use` start event from the crate would let `awaitsWords` cover that stretch.
- Sync: a reply being written on one device would reach another with its `writing` block and read as interrupted there. The rule needs the writing device's id, or an age, before threads sync live.
- Nothing is flushed when the app quits: up to the debounce's 250 ms of text can be lost from an interrupted reply.
- A reply interrupted before this was built carries no mark and reads as it did.

## The context pack

`buildPack` is pure over readers the app injects (facts, entities, primitives, the grant check), tested in Node. What a request carries, in the order the API reads it: the tool schemas; the system prompt; the thread as turns; then the owner's message, with the context ahead of it in the same turn. The context is one `<context>` block, a section per registry id in the order the reads were declared: the declared facts, the owner's own word first; the declared entities, newest first; the declared primitives by kind in the window from seven days back to fourteen ahead (tasks without a window, since a routine has no due). Each row is one compact JSON line under its registry id; every string passes the scrub; a mirror row is wrapped as untrusted, and the system prompt says what that means. A domain may shape what the pack carries of its rows (`pack` in its bindings, `engineering/domain-module.md`), which `readers.ts` applies: Sky's `forecast` row goes as the current reading and seven days from today, with no hours (`forecastForPack`, D-85), and the `forecast` tool answers the rest. Only the newest message carries a context block, so a follow-up reads the workspace as it is now.

The thread is replayed as it happened (`turnsOf`): the owner's words, and each reply's words with the tools it called and what each answered, as the API's `tool_use` and `tool_result` pairs, rebuilt from the `call` a tool block stores. So a follow-up knows what was drafted, what a tool said and what was declined. A call's result carries what became of the card it left (`kept by the owner`, `discarded by the owner`, not yet either); a call the app closed on answers that it was interrupted; a result over 2,000 characters is replayed whole only from the last reply, and from an earlier one says to call the tool again. Inputs and results pass the scrub. Trimming drops a whole stored message's turns at a time, so a call never loses its answer, and a thread that opens on a reply (a tool run from a button) is given the owner's turn the API requires.

Tiering is the registry's: a T3 read cannot be built (`gardener:never`; the builder refuses it first), a T2 read is included under a live grant and otherwise listed as `locked`, T0 and T1 are the default. The budget is `ceil(chars / 4)` against the model's context less the output reserve, and the per-request cap: over it, the oldest entity rows go first, round-robin across ids, then the oldest thread turns; facts, the focus rows and the message never go, and each trimmed id is named in the chip. The "can see" chip is literal: one chip at the composer's foot with the row count, opening the kit's `CanSee` popover with every id that has rows after trimming (an id with none is not listed), each named as the owner knows it (`registryLabel`: a fact's name, else the id read as words) and the rows behind each named as the row opens (`labels.ts`: a fact by its value, an entity or a primitive by its name). The list inside is the kit's `ReadList`; the audit log's entry shows the same list, so what was read looks the same before and after the request. A locked id is a T2 read no grant allows; its row says so and offers a standing read grant through a confirm sheet. The tool card's info button and an audit row open the same kind of popover (`DetailPopover`).

### The system prompt

`persona()` (`packages/shared/src/gardener/persona.ts`) writes it as a briefing addressed to the model, in the second person, with the reason beside each rule; the Gardener it asks for speaks in the first (`design/brand.md`). In order: what Eden is and where the conversation is happening (the domain the panel was opened from, by its name); the enabled domains, each as `Name (id): what it holds`, since the owner says Hearth and the tools and rows say `kitchen` (the lines are `DOMAIN_BLURBS` in `tools.ts`, one per declared domain, which a test holds to); the voice; what the context block is, that it is a snapshot the owner sees the same list of, and what empty, locked and trimmed mean; the untrusted rule; that the scrub's `[email]`, `[phone]` and `[number]` are deliberate; how a tool call looks to the owner (a card, a draft that is not saved until kept, a confirm, a decline that is an answer, an error to fix or to report); the grade and that it is the owner's to change; and Markdown, for a reply read in the panel. It never lists the tools: the request's tool list is the one list. A request with no tools is told nothing about them.

It is two system blocks: the stable one, cached, and the volatile one, so a thread's follow-ups hit the cache. The volatile block gives the clock as the owner reads it (`Now: Wednesday 2026-09-30, 09:40 (America/Chicago)`: the weekday, the day and the time in their zone, never a UTC instant the model would have to convert) and the can-see list with the locked and the trimmed ids.

`request.snapshot.test.ts` renders the whole prompt for a fixture pack to `__snapshots__/system-prompt.chat.txt`, and a delegated request's to `system-prompt.delegated.txt`, so the words a request carries are a file to read and a change to them is a diff.

### A delegated request

A model-backed tool's request is not a conversation, so it does not get the chat's prompt. `persona()` in `mode: 'delegated'` says it is one job inside Eden whose reply a program reads, asks for the job and nothing around it, names the owner's language for any prose, and keeps the domains, the context frame, the untrusted rule and the scrub line. It has no voice rules, no tools paragraph and no grade.

A handler that parses JSON gives its delegate a `schema`, built with `answer` (`@eden/shared/gardener`): every object closed and every field required, so a field with nothing to say is an empty string, a zero or an empty list, and the parser drops those. The schema's field descriptions carry what the old "Answer as {…}" lines did, and the prompt is left to say what the job is for: use what expires soonest so less is wasted, keep an event evening light. `parseJson` still reads the answer, so a provider without structured output degrades to the old behaviour. A delegate with no schema answers in prose (`brainstorm`, the day briefing).

Before a request is made a delegate's `check` may refuse the input. After it, an answer cut short at `max_tokens`, one the owner stopped, and one that is not the JSON asked for are each an error result with no card: half an answer is never drafted.

`summarize-day` is the one delegate that gathers across domains (`substrate-tools.ts`): the day's events with their times, the tasks due, overdue (on the day itself) and done, and, when Sky is enabled and holds a reading for the day, its forecast and today's alerts. It answers `briefing`, short Markdown the chat gives the owner as it stands. Handoff: a birthday is an Event of kind `birthday` once People is built, so it reaches the briefing through the day's events; the line should then say whose it is (`product/domains/people.md`).

## The scrub

`scrub(text)` replaces emails, phone numbers and account-like numbers (eight or more digits, spaces or dashes between groups) with `[email]`, `[phone]` and `[number]`, leaves dates, times, ULIDs and stamps alone, and is idempotent (D-26). It runs on every row string, on the owner's message and on each turn of the thread, never on the system prompt.

## Tools

`toolIndex(declarations)` is the substrate's tools declared in code (`SUBSTRATE_TOOLS`: `create-task`, `complete-task`, `summarize-day`, `what-you-know-about-me`, `log-quick`, `propose-fact`) and every enabled domain's tools from its manifest, each joined to its input schema and description. Anthropic's tool names take no dot, so a domain tool is `<domain>_<id>` on the wire; overrides stay `<domain>.<tool>` and grants stay bare tool ids. Schemas carry `additionalProperties: false` on every object and no numeric or string constraints; the tools that write or draft are marked `strict` (the API holds their input to the schema) and the read tools are not, since the API takes twenty strict tools at most and a request carries the whole index. Sixteen are taken (the substrate's four, Hearth's ten, Toolbench's two), so a domain that changes many things does it with a few batch tools, as Hearth does (D-108): one tool per kind of row, with lists to add, change and remove. `validateTools` refuses a read outside the registry, a T3 read, a duplicate or malformed wire name, a schema the API would not take and more strict tools than the API takes, and the test runs it over the manifests.

A description is the tool's whole contract with the model, which sees nothing else of it, so each one says what the tool does, what comes back, when to use it and what it cannot do; every parameter has its own line. Two are built from data, so they cannot drift from it. `log-quick` takes one `action`, an enum of `<domain>.<action>`, narrowed by `toolIndex` to the quick actions of the domains it is given that `QUICK_ACTION_WORDS` has a line for (what the action does, what its `value` is); with none, the tool is left out. `propose-fact` takes a `type` from `PROPOSABLE_FACTS` (the live fact types the substrate does not derive) and its description lists the shape of each type's value, written from `FACT_SHAPES`. `__snapshots__/tools.txt` is every tool as the API is given it.

What a tool answers is written for the model too. A result is plain fields, with a `note` where the next step is not obvious: a drafting tool answers `status: 'drafted'` and that nothing is saved until the owner keeps the card. An error says what was wrong and what to pass instead (an unknown id names the id and where ids come from; a day the forecast does not reach names the days it holds), and nothing falls back silently to a default the model did not ask for. A decline is `cancelled` with words that say not to retry. Every result passes the scrub before it is sent. A delegate's `check` refuses an input it cannot work on (an id that does not resolve, neither of two ids) before a model is resolved, so no request is spent on it.

Handlers are the app's. `DomainBindings.tools` maps a tool id to a handler, `run(input, ctx)` for a plain or write tool and `delegate` (a prompt, a parser, a card) for a model-backed one. A `run` handler may give a `preview(input)`: what the call would do in the owner's words, one line per change with each row named by its name, which the tool card shows in place of the raw input while it waits on the confirm (the input names rows by id, which says nothing to the owner about a delete). A delegate that reads files names them with `Delegate.files` (`capture-haul`, `import-recipe`), which replaces the single image a delegate once carried: the pack's own attachment handling builds the content blocks ("Attachments", below), and a delegate that names files and is given none is not run and answers `no-files`, unless `filesOptional` allows it (a recipe pasted as text). The files a tool may read arrive as `ToolContext.files`: in a conversation the ones on the owner's message, else on the latest earlier message that had any; for a tool a page runs, the ones the page staged. A tool takes no attachment id as input, because the model cannot name an attachment. A result that answers nothing carries `ToolResult.failure` ("A tool run from a page"). `DomainBindings.quickActionHandlers` maps a quick action id to its store write, which `log-quick` dispatches to and the Quick Log sheet (#27) reuses. The substrate's handlers live in `shell/gardener/substrate-tools.ts`. A declared tool with no handler answers "unavailable", and the shell logs the list of them when it starts (`missingHandlers`). The page at `/gardener/tools` lists the index for the owner: one row per tool with its owner, access, grade and the count of ids it may read, the substrate's first; a row unfolds beneath itself (`DataTable`'s `detail`) to `ToolAbout` (`shell/gardener/ToolAbout.svelte`: the description, then access, grade, whether it asks first and the reads by name), the same body the conversation's tool popover shows, with the input schema folded beside it and a warning row for a tool without a handler. The Gardener tab and the panel's header link to it. A domain's `tools.ts` imports only its own store and the shell, as the isolation lint requires.

## Attachments

The owner's files on a message (D-82 to D-84). `packages/shared/src/gardener/attachment-limits.ts` is the one place the numbers live: what is accepted (`ACCEPT`, MIME types and the extensions beside them, since an engine leaves `type` empty for `.md`), ten files a message, the size each type may be as stored, the edge and weight an image is sent at, 20 MB a request as sent, and the paste threshold.

**In.** The panel is wrapped in the kit's `Dropzone`, off while the thread list is up or nothing can be asked; the composer's foot has a `FileButton`; the `Composer` hands pasted files and long pastes to `onfiles`. All three go through one check (`checkStaged` in `shell/gardener/files.ts`: the kit's `checkFiles`, then each type's own cap and that the file has bytes), and a refusal is one toast in the app's words. A staged file is a `FileChip` above the message, measured while it waits (`measure`: `createImageBitmap` and an `OffscreenCanvas`, since the CSP has no `blob:`; a 256 px JPEG thumbnail as a data URL). The send waits for the measuring.

**Stored.** `runtime.ask(text, staged)` writes the files first (`storeFiles`: `attachBytes` each, `photo` or `document`, `part-of` the thread, `captured` holding the pixels; all or none) and then appends the owner's message as `[...attachment blocks, text?]`. An `attachment` block is `{ id, name, mime, size, hash, width?, height? }`. `ask` answers false when nothing was sent, and the panel puts the words and the files back. `MessageBlocks` draws the blocks as chips in the owner's bubble, the thumbnail from the row (`threadAttachments`), `missing` when the row is gone. `segmentsOf` skips the block.

**Sent.** `buildPack` takes the message's files as `attachments` and finds the earlier ones in the thread. A file is a placeholder part of its turn, counted by what its block says (`attachmentTokens`: an image by its sent pixels over 750, text by its bytes over four, a PDF by its bytes over forty with a floor; `sentBytes`), so trimming needs no bytes. Past 20 MB as sent, and then past the budget once the entity rows are gone, the earlier turns' files become `[attachment no longer sent: name]`, the oldest turn's first; then whole exchanges go as before. Only then does `PackReaders.attachment` read what is left (`readForPack`: `readAttachment`, an image over the sent size scaled to a JPEG, kept in memory for the next turn). An image is an `image` block, a PDF a `document` block, a text file `<file name="…">` with its text scrubbed, and a file whose bytes are gone `[attachment unavailable: name]`. The message's files come after the context and before its words; a message of files alone sends no text block. `pack.attachments` is what the audit entry keeps, `pack.attached` the names the "can see" block lists, and a `document` raises the tier to T2.

**Asked.** A request with an image or a PDF in it, the message's or an earlier turn's, resolves its grade with `vision` beside `tools`. A `document` in the pack records a per-request grant on `document` (origin `confirm`), whose id joins the entry's grants. A delegated request that carries files (`capture-haul`, `import-recipe`) counts them in its estimate and records the same grant, in a conversation or run from a page; its audit entry lists them under `attachments`.

Handoffs:

- `capture-haul` asks the model for a box around each item it sees, for the item's picture (D-90). How well the light grade draws one has not been seen live; a box that shows nothing, or most of the photo, is dropped in `haulRows`, and the per-tool override (D-74) is the first thing to try if the pictures are loose.
- In a conversation `capture-haul` and `import-recipe` send their images twice: once in the chat request, as the message's files, and once in the delegated one. The delegated request is the one that reads them; the chat request could carry placeholders for a message whose files a tool will read.
- A draft settled after the owner switched threads may stay pending: `threads.patch` reaches only the open thread or one that is held, and a capture or a recipe draft is settled from the domain's surface, which may be long after its card was pressed.
- The mobile chat (#19) needs the same staging and chips, with the camera and the photo library in place of the drop zone; `files.ts` has nothing desktop in it but lives under `apps/desktop`.
- Nothing removes an attachment's file: a deleted thread tombstones its attachment rows and the bytes stay in `attachments/`. A sweep of files whose rows have been tombstones past the undo window belongs with the data layer.
- Sync does not carry attachment bytes. On another device a message's files read as `missing` and the model is told they are unavailable; the bytes should cross as encrypted blobs (D-21).
- A chip in a sent message does not open its file: there is no asset protocol and no `blob:` in the CSP. Thumbnails are the data URLs `measure` makes, in the panel and in Hearth's capture sheet alike; opening the stored file itself wants one decision on how it is shown.
- The estimates are heuristics; the provider's token-counting endpoint would make the budget check exact, PDFs most of all.
- A HEIC or TIFF dropped or pasted on the composer is refused by type. Hearth's capture redraws a HEIC as a JPEG itself before anything else (`domains/kitchen/staging.svelte.ts`); the composer could do the same on the way in, which would take what macOS copies from some apps. That redraw relies on the webview decoding HEIC, which is assumed and not verified in the Tauri app.
- The API's own limits (per-image bytes and pixels, request size, PDF pages per model) were taken from memory when the caps were chosen, not checked against the current reference; the caps sit well under them, and should be read against it before they are raised.
- Not verified in the running app: the raw-body `attach_bytes` call with a large file, `dragDropEnabled` reaching the window through each config overlay, whether WKWebView tells a drag's types before the drop (the overlay falls back to the count), and what the clipboard gives for an image copied in Finder.

## Budgets and estimates

The policy row holds the monthly cap (10 USD by default) and the per-request token cap (the model's context when unset). An estimate before sending assumes the pack's tokens in and `maxTokens` out at the resolved model's pricing row; the entry after records the usage the provider reported, cache reads priced at their own rate. This month's spend is the sum of the audit's `costUsd` since the first of the month in the owner's zone.

## The audit log

An entry's `attachments` (migration 7) lists the owner's files the request carried, each by hash, type, size and an image's pixels (D-83). `audit_entries` is this device's: 90 days, never exported, never synced, never cleared by a replace, swept when the workspace opens. An entry is written once its request has ended; one the app closed on is written at the next start with the outcome `interrupted` ("A request that never settled"). An entry holds what `product/substrate/ai.md` lists; `reads` carries the row ids read, which is what "used by N requests" on the profile counts (`audit_usage`). The page at `/gardener/audit` lists the entries and unfolds one beneath its row to its reads, tools, grants and thread; the Gardener tab, the panel's header and the profile page link to it.

## Threads and policy

`threads` and `messages` are rows of the workspace: stamped, tombstoned, exported in the full bundle and merged by stamp. A message's `blocks` is JSON the frontend shapes, as a fact's value is: text, tool cards with their state (`pending`, `running`, `done`, `failed`, `cancelled`), proposal and draft cards, the can-see snapshot, an error, and the `writing` mark of a reply whose request has not ended. A card stored `running` or `pending` by a request that is no longer live reads as cancelled. The blocks are stored in the order they happened and drawn in it: `segmentsOf` (`packages/shared/src/gardener/segments.ts`) turns them into text, single cards and runs (two or more consecutive `read` calls that are running, done or cancelled), and the panel draws a run as the kit's `ToolRun`; the mobile chat (#19) draws from the same function and the same component. A reply's text is Markdown: the chat's persona asks for it (`markdown` on the pack request; a delegated request leaves it off, since a handler parses its answer) and the panel draws it with the kit's `Markdown`, which never injects HTML. A message's foot shows its `createdAt`, so a reply's "Received at" is when it began. A thread's tier is the highest tier it read; a T2 thread shows the lock and stays out of future packs unless the owner includes it, which records a per-request grant on the T2 id that made it so.

`policy` is a generic key-value table of workspace policy (D-37). The row `gardener` holds the owner's sparse edits over the seed, the overrides, and the two caps. The conversation's grade is a per-device setting.

## The development clamp

In `development` (`yarn dev`) and in the browser (`web`) the light and the standard grade resolve to the seed's light model and the deep grade to its standard one (D-81); every override is left out, and the deep model is never reached. So developing spends little by default, and the standard model, which reasons where the light one does not, is one switch of the chip away. Staging and production use the real map. The audit entry records the model that ran. A `deep` tool still confirms under the clamp, since the confirm is about the tool's cost class; the sheet shows the standard model and its estimate, and the Gardener tab says the clamp is on and names both models, as does the info button just left of the status bar's grade switch (the kit's `StatusBarNotice`).

## The browser fallback

`yarn dev:web` has no crate: `hasSecret` is false, `gardenerSend` rejects `unavailable`, and the panel says the Gardener runs in the installed app. Threads, messages, the policy and the audit log work in the engine, so the panel is developed against `FakeTransport`, a scripted stream; a message that names the moon is answered with a line, three `sun-and-moon` calls and an answer, which exercises the order of a reply and the fold. A request held to a schema is answered in that shape (`shell/gardener/transport.ts`): a canned haul for `capture-haul`, a canned recipe for `import-recipe`, and for any other schema an answer that is complete and empty. So the capture sheet and the recipe import can be walked in the browser.
