## The key

Keys are T3 and per device (`product/substrate/integrations.md`, "Secrets"): they live in the OS keychain, never in the Vault, which the AI subsystem structurally cannot read, and never in the workspace database. `SecretStore` follows the DB key provider's split by target system:

| platform | store |
|---|---|
| macOS, iOS | the Keychain, service `eden.secrets`, account = the secret's name, this device only, readable after the first unlock. The unsigned development build on macOS uses the file store instead: a rebuilt unsigned binary cannot read what the last one wrote to the Keychain |
| Android | the Keystore through `EdenSecrets.kt`, the same wrapping pattern as the DB key; written and unrun (the checklist in `engineering/data-layer.md`) |
| Windows, Linux | `<app data dir>/secrets/<name>`, mode 0600, until their keychain paths are ported |

The Anthropic key is `anthropic-api-key`. Three commands touch the store (`set_secret`, `has_secret`, `delete_secret`) and none answers a value: the adapter reads it inside the crate, and the webview only ever learns "present" or "absent". A key never appears in an export, a diagnostic, an audit entry or an error message; the adapter strips URLs and headers from a network error before it is emitted.

## The request

The webview builds the whole request and the crate adds only the key. `gardener_send(request, onEvent)` takes `{ id, model, maxTokens, system, messages, tools, outputFormat?, effort? }` (`tools` goes out as given, a tool the provider runs itself among them; `outputFormat` is a JSON schema the reply is held to, sent as the API's `output_config.format`; a delegated request's alone; `effort` is the level the model is asked to work at, sent as `output_config.effort`), records the egress (`anthropic`, the URL and the body's bytes; D-71) and POSTs to the Messages API with `stream: true`. The stream comes back over a Tauri channel as events:

| event | carries |
|---|---|
| `start` | the message id and the model that answered |
| `text_delta` | a piece of the reply |
| `tool_use` | one complete tool call: id, wire name, parsed input |
| `thinking` | one whole reasoning block as the provider sent it (`thinking` with its signature, or `redacted_thinking`) |
| `server_block` | one block of a tool the provider ran on its own side (D-132), whole, when it closes: the call (`server_tool_use` with its id, name and input), or its result (`toolUseId`, `results` as the addresses and titles returned, `error` as the provider's code or `null`). The pages' encrypted text is never handed over |
| `usage` | tokens in, out, cache read and cache written; once at the start, once at the end. The closing one is read in full, since a server tool's results grow the input, and carries `searches`, the web searches the provider ran |
| `stop` | the reason (`end_turn`, `tool_use`, `max_tokens`, `refusal`, `cancelled`) and the refusal's category |
| `error` | the provider's status and message, or a network failure mid-stream |

`gardener_cancel(requestId)` aborts a stream. The adapter never sends `thinking` (the current models decide for themselves) nor `tool_choice` (a forced choice is refused by the current models). A model that reasons returns its reasoning as blocks, and the API wants them back unchanged while a request continues: the runtime keeps each `thinking` event in its place among the reply's blocks and sends it back with the tool results of that request, and keeps it nowhere else (never on the thread row, never in a later request). That reasoning counts toward `max_tokens`, so a model the seed marks `thinks` is given room for it on top: 4096 more for the conversation, 2048 more for a delegated request, and the estimate is made from the same figure. A model the owner adds carries no mark and gets none; a 400 is shown as the provider wrote it, which is how Fable's retention requirement reaches the owner. Effort is a dial of the model's row (D-146): `efforts` lists the levels it takes as the provider names them, `effort` is the one every request to it is sent at (the conversation, a delegated request and a research request alike), and a row with no levels is sent none, since a model without the dial refuses the field. The seed runs the three models that reason at `medium` and lists no level for the light one; the owner's level is a `ProviderEdits` model edit (`effortEdit`), chosen beside the grade in Settings → Gardener, and one the model does not take is refused like any other edit. The room for reasoning is the same at every level. Changing a model's effort makes the provider's cache of a running conversation cold once. No key on this device is `gardener:no-key` before anything is sent.

## The loop

One owner message is one request, and one request is one audit entry. In order:

1. No key: the grey chip and the notice. Budget: this month's spend plus the estimate over the cap declines with a link to the Gardener tab (D-7).
2. `resolveGrade` at the conversation's grade (`settings.gardenerGrade`, the chip's switch); unavailable says why; a move above the grade for a need is confirmed with its estimate first (D-74).
3. `buildPack` (below). Over the per-request token cap declines.
4. The owner's message and an empty reply are rows of the thread; the can-see block is written from the pack, and the rows the reply's tools read join it as they are read (D-149). The reply carries a `writing` block while its request runs, and the request's audit entry is kept on the device as open (below).
5. The request streams. Text lands in the reply's text block. A `tool_use` runs its handler:
   - a **plain** tool, and a `write-draft` one, runs inline; its card is `running` and settles `done`, and its answer becomes the `tool_result`. A handler that throws, or answers `{ error }`, settles the card `failed` with the error on it, and the model gets the same error result; an answer with `cancelled: true` (a cost declined, the owner's Stop) settles it `cancelled`;
   - a **write** tool asks the grant store (`subject` the model id, `resourceType: 'tool'`); a standing grant runs it with an undo toast; otherwise the tool card waits `pending` with its confirm and the request pauses; confirmed, it is `running`. Confirm records a `per-request` grant (`origin: 'confirm'`), or a `standing` one for a tool of the substrate's named in `STANDING_ON_CONFIRM` (`log-quick` and `update-tasks`: the Quick Log's first-use pattern, D-124), and runs it; cancel answers the model with an error result;
   - a handler may **ask** for one call, whatever the tool's access or grant (`asks(input, ctx)` on a `run` handler): `update-tasks` asks when the call deletes, and `read-page` for an address the owner did not write (D-126). The card waits `pending` with its confirm, and a confirm that was asked for records a `per-request` grant for a write and none for a read, never a standing one;
   - **the guard** (D-126, D-132): in a conversation that holds a page that was read, or what a searching tool answered, every `write` confirms, standing grant or not, and that confirm records `per-request`. `holdsPage` reads it from the stored thread before each request, so it outlasts a restart, and is told which tools search (`needs` holds `search`); the runtime marks the thread the moment a `read-page` call or a searching tool's call settles;
   - an **act-external** tool always takes the confirm path; no Phase 1 tool declares it;
   - a **model-backed** tool is a delegated request: `resolveTool` with the policy's overrides, a confirm when it runs at `deep` or above its declared grade, its own pack from its declared reads alone with the tool's prompt as the message, the files its delegate names (`Delegate.files`, below) and no tools (bounded, never a loop), a system prompt of its own and, where the handler parses JSON, the schema its answer is held to ("A delegated request", below), its own audit entry with `parentRequestId`, and its parsed answer as the `tool_result` and, for `write-draft`, a draft card. A delegate with `research` makes a research request first ("A research request", below): the one server tool, which the provider loops on its own side, so Eden still loops nothing. Its place in the thread is its tool card alone: the delegated answer is read by the handler and never streamed into the thread, and no holder message is written (the audit entry's `threadId` and `parentRequestId` walk it back to its chat).
6. `stop: tool_use` continues the same request with the assistant's blocks and every tool result, six rounds at most. The sixth round's results go back with a line saying it was the last, and one more request is made for the words that close the reply, so a reply never ends on a tool card; a tool asked for after that is not run. Every round's request carries a cache breakpoint on the last block of its last turn (`withBreakpoint` in `cache.ts`, D-147), so the round after it reads the thread, the context and the earlier rounds from the provider's cache and pays the input price only for the newest results; the first round writes that prefix at the write price, a quarter over, which a reply of one round with no follow-up never earns back. The provider looks back twenty blocks from a breakpoint for an earlier entry, so a round of more than about nine calls misses once. The pack's own breakpoints, on the settled history, are left where they are ("The context pack"). A tool whose result is text (`read-rows`, `agenda`) is sent as that text; any other result is sent as JSON. A result that carries `reads` (D-148) is merged into the request's audit entry (`reads`, `entities`, `grants`), raises the thread's tier and joins the reply's can-see block. `end_turn` settles. `max_tokens` marks the reply cut short with a Continue. `refusal` shows the category. An error shows the message; a network failure, 429 and 529 offer a retry (below).
7. The `writing` block comes off the reply. The audit entry is written with the usage, the cost from the pricing row, the reads with their row ids, the entities, the tools with their confirm outcome, the grants, and the outcome. The thread's tier rises to the highest tier read. The profile's usage counts are read again. At 80 % of the cap the warning shows once a day.

Draft cards are the runtime's: a task, a plan (tasks and a `shop-day` Event through a batch), a grocery list, code (copied, never written to a file), a capture (stock rows read from the owner's files), a recipe, and the proposal card (`profile.propose`, D-72). A commit is an ordinary store write with an undo toast and a feed entry; the card's state is settled on the message row. A `capture` and a `recipe` draft are not committed in the panel: the card's button hands the draft to its domain's `openDraft` binding (`engineering/domain-module.md`, "Bindings"), which opens it on the domain's own surface, Hearth's capture sheet at its rows or its Recipes pane as an unsaved draft, and the card settles when the owner keeps or discards it there (D-86). A draft is shown as its own message after the reply, the Gardener's bubble in honey (`GardenerMessage` `tone="honey"`) with the draft's title as its header and no access badge. A drafted task is a todo, a routine or a habit by what the draft holds (`taskFromDraft`, `@eden/shared/tasks`): a target makes a habit, a recurrence a routine, anything else a todo, which is due today when the draft names no day, as a line added on Today is, with a time of day joined into the due. The card says a routine's repeat and a habit's target in the words Today uses. `draft-tasks` leaves the task card for one task and the plan card, with no events, for several; a kept plan is one batch and emits no signal (D-75).

### A tool run from a page

A page may run a model-backed tool itself, with no conversation (D-86). Hearth's capture sheet and its recipe import do, and Meadow's Find more, its listings search (the weekly one too, D-134) and its import's tagging (`engineering/meadow.md`).

- `runtime.runDirect(toolKey, input, { files, confirmed })` takes `<domain>.<tool>` and runs a `read` or a `write-draft` tool that has a delegate; a write keeps its card and its confirm in a conversation. It is the delegated request of step 5 with no thread: the same resolution, pack, budget check and audit entry, whose surface is `delegated` and which has no thread and no parent, and lists the files under `attachments` by hash, type, size and pixels (D-83). It answers the tool's `ToolResult`.
- `ToolResult.failure` is why nothing was answered, as a code the page puts its own words to: `busy`, `no-key`, `unavailable`, `budget`, `network`, `refusal`, `max-tokens`, `cancelled`, `unreadable`, `empty`, `no-files`, and for a searching tool `search-refused` (the provider answered the research request 400 or 403, as when web search is off for the organisation; the `output`'s error is the provider's own words) and `search-failed` (no notes came, or notes with no search result behind them). The `output` beside it is still written for the model.
- `confirmed: true` says the page showed the estimate and the owner went ahead, so the cost confirm is not asked again and the entry records it as confirmed. Without it a request that owes a confirm is declined: the confirm sheet is the panel's, and the panel may not be open.
- `runtime.previewDirect(toolKey, input, { files })` answers the provider, the model and the estimate, or why the tool cannot run (`no-key`, `unavailable`, `budget`). It reads no file and sends nothing: the files are counted by their blocks. For a searching tool the estimate is both requests', and a provider with no search tool is `unavailable`.
- One stream runs at a time. While a direct run is under way `runtime.direct` is true and the panel's send waits; a direct run asked for while a request streams answers `busy`.

### A request that never settled

The provider's stream cannot be resumed, so a request the app closed on (a quit, a crash, a reload of the webview) is lost from where it stopped. Two things keep it from being lost silently:

- **The reply says so.** The `writing` block is on the reply from the moment it is appended and comes off when the request ends, however it ends. A reply that still has it and is not the one the runtime is writing (`runtime.live`) reads as interrupted: the bubble is drawn even when nothing arrived, with what did arrive, its cards read as cancelled, and a notice. This is derived when the thread is read, as a card's state is; nothing is rewritten.
- **The log says so.** `openRequests` (`packages/shared/src/gardener/open-requests.ts`) keeps each request's audit entry in `localStorage` (`eden:gardener-open`) from the moment it is sent, a delegated request's too, with the outcome `interrupted`, the pack's estimated tokens in, and then whatever usage the provider has reported; writing the real entry takes it away. What is still there when the app next starts (`runtime.settleOpen`, once, when the panel first opens and before the first request) is recorded as it stands, so the month's spend counts it. The output tokens of a cut request are the last the provider reported, which may be none.

**Retry** is offered on a reply that was interrupted, or that failed with `network`, 429 or 529, while it is the thread's last message and follows the owner's. It fades the reply, deletes it for good (`delete_message`, a tombstone; no undo), and answers the owner's message anew as a new request with its own entry; the interrupted one keeps its entry. A write the deleted reply had already made stays made, and the new request may make it again.

A request writes to its own reply whichever thread is open: the reply is held by the thread store (`hold`, `release`) while it is written, so opening another conversation or a new one loses nothing, and opening its thread again shows it still being written. One request runs at a time, so the composer is busy in every thread until it ends.

The panel and the phone's sheet draw one log (`ChatLog`), so the notice, Retry and the sprout below are the same on both. While a reply is awaited the panel shows the kit's `Sprouting` (D-80). Before the reply exists (the pack being built, the budget read) the runtime's `preparing` holds the thread's id, and the panel draws one bubble with the sprout after the thread's last message, unless the cost confirm is up; the same row stays while the reply is live and has no segment, so the sprout never starts over between the two. Once the reply has a segment its own bubble draws the sprout after its cards whenever `awaitsWords` (`packages/shared/src/gardener/segments.ts`) says so: the last segment is not text, no card in it is running or pending, and it is not an error. The browser's scripted transport waits 1.2 s before its first word of each round so the sprout can be seen there.

Handoffs:

- The tools page and the tool popover show a tool's description (`ToolAbout`), which is now written for the model: what comes back, which ids to pass. An owner's line per tool, in the locale files, would read better there.
- The sprout does not show while the model writes a tool call after its words: the stream reports a call only once it is whole, so the last segment is still text. A `tool_use` start event from the crate would let `awaitsWords` cover that stretch.
- Sync: a reply being written on one device would reach another with its `writing` block and read as interrupted there. The rule needs the writing device's id, or an age, before threads sync live.
- Nothing is flushed when the app quits: up to the debounce's 250 ms of text can be lost from an interrupted reply.
- A reply interrupted before this was built carries no mark and reads as it did.

## The context pack

`buildPack` is pure over readers the app injects (facts, entities, primitives, the grant check), tested in Node. What a request carries, in the order the API reads it: the tool schemas; the system prompt; the thread as turns; then the owner's message, whose first block is the head: the clock, the `<context>` block and, in a conversation, the `<index>`.

A request reaches the registry ids its tools declared (D-31), and what it carries of them depends on who asks (D-148).

- **A tool's own request** (delegated or research) has no tools to fetch with, so it carries every row it declared: a section per registry id in the order the reads were declared; the facts, the owner's own word first; the entities, newest first; the primitives by kind in the window from seven days back to fourteen ahead (tasks without a window, since a routine has no due), and every task, since its tool works from the tasks it declared (`summarize-project`).
- **A conversation** carries little. Up front, whole: the facts the substrate owns (`preferred-name`, `home-area`) and the facts owned by the domain the panel was opened in (the registry's `owner`), and the rows it was opened on (`focus`: an idea, today). Every other id in reach is one line of the `<index>`: `- stock-item (kitchen): 14 rows`, or `locked` for a T2 id no grant allows. The index is counted from the same reads, so a `task` line counts what `tasksForPack` keeps (`@eden/shared/tasks`; D-125: what is open, the todos and checklists done in the last seven days, a task the conversation is about) and an event line the window. The model fetches rows with the substrate's `read-rows`, and `agenda` answers a day.

Both paths read through one function, `sectionReader` in `pack.ts`: the tier gate and the grant check, the domain's own shaping of its rows (`pack` in its bindings, `engineering/domain-module.md`, applied by `readers.ts`: Sky's `forecast` row goes as the current reading and seven days, with no hours, D-85), the trimmed tasks, the window, the newest first with the focus rows ahead. `readRows` is what `read-rows` answers: one id's section, or the rows named by `ids`. So a store's address stays out on the tool path as it does up front (D-101), and a mirrored row is untrusted on both. A section longer than `READ_ROWS_CHARS` (12,000) asked for without `ids` answers each row's `id` and name instead and says to ask by `ids`; nothing in the data layer searches or pages yet. An id outside the conversation's reach, a T3 id and a T2 id with no grant are refused in words the model can pass on, and nothing is read.

**How a row is written** (`rows.ts`, D-151) is the same wherever it is sent. A row goes without what only the store needs (`uri`, the stamps, `links`, the mirror's fields) and without any picture held inline (a `data:` value such as a place's thumbnail, D-154), with an entity's payload fields beside its `id` under the names the write tools take, every instant cut to the minute, every string through the scrub. A section of three rows or more is a table: a header of the field names (`id` first, the rest in the order the rows first carry them, the `type` or `kind` the heading already says left out), then one `|`-delimited line a row; an empty cell is a field the row does not have, a list or an object is JSON in its cell. Facts, the rows a conversation was opened on and a section of one or two rows stay one JSON object a line. A cell cannot start a row or leave its column (`\|`, `\n`, `\\`), and a mirrored row keeps its own `<untrusted source>` wrap, which nothing inside can close (`</untrusted` is written `&lt;/untrusted`, in a JSON line too). The bytes follow from the rows alone, so the same workspace writes the same request. Whether a section is a table is settled before the budget trims it, so trimming a row only ever shrinks it. `agenda` answers through the same writer (`agendaText`): a heading a day, then each list under its name.

Only the newest message carries a head, so a follow-up reads the workspace as it is now.

**The cache (D-147).** The provider caches a request by the bytes of its prefix: the tools, then the system prompt, then the messages. Three things keep that prefix the same from one message to the next. The tools are sent in one order, by wire name, whatever panel asks (`toolsFor`). The system prompt is one block that holds nothing of the clock, the panel or the pack. And the settled history ends on a breakpoint: the turn ahead of the last reply is marked, and so is the turn ahead of the reply before it, which is where the last request left its own, so the read is an exact hit however many blocks the reply between them holds. The last reply itself is behind no breakpoint, since its long results are whole now and left out next time. With the system block's and the moving one the runtime adds each round, that is the API's four. A miss is never an error, only a full-price read: a card kept or discarded after its reply was replayed, a thread trimmed from the front, more than five minutes between messages, a change of model or of effort, a tool added.

The thread is replayed as it happened (`turnsOf`): the owner's words, and each reply's words with the tools it called and what each answered, as the API's `tool_use` and `tool_result` pairs, rebuilt from the `call` a tool block stores. So a follow-up knows what was drafted, what a tool said and what was declined. A call's result carries what became of the card it left (`kept by the owner`, `discarded by the owner`, not yet either); a call the app closed on answers that it was interrupted; a result over 2,000 characters is replayed whole only from the last reply, and from an earlier one says to call the tool again. Inputs and results pass the scrub. Trimming drops a whole stored message's turns at a time, so a call never loses its answer, and a thread that opens on a reply (a tool run from a button) is given the owner's turn the API requires.

Tiering is the registry's: a T3 read cannot be built (`gardener:never`; the builder refuses it first), a T2 read is included under a live grant and otherwise listed as `locked`, T0 and T1 are the default. The budget is `ceil(chars / 4)` against the model's context less the output reserve, and the per-request cap: over it, a tool's request loses its oldest entity rows first, round-robin across ids, and a conversation, which carries none to lose, its earlier files and then its oldest turns; facts, the focus rows and the message never go.

**The eye (D-149).** A reply's first block is its can-see block: the ids sent up front with their rows, the T2 ids in reach that are locked, and whether the thread was trimmed. As the reply's tools read rows (`ToolResult.reads`), the runtime merges them into the block and into the audit entry, so both list exactly what the reply read. The panel draws it as an xs eye beside the copy glyph in the foot of the thread's last reply (`ReplyEye.svelte`, through `GardenerMessage`'s `actions`), opening the kit's `CanSee` popover: every id with rows, named as the owner knows it (`registryLabel`: a fact's name, else the id read as words), the rows behind each named as it opens (`labels.ts`: a fact by its value, an entity or a primitive by its name), and each locked id with an Allow that records a standing read grant through a confirm sheet. The composer has no chip, and nothing is read to preview a message. The list inside is the kit's `ReadList`; the audit log's entry shows the same list. The tool card's info button and an audit row open the same kind of popover (`DetailPopover`).

### The system prompt

`persona()` (`packages/shared/src/gardener/persona.ts`) writes it as a briefing addressed to the model, in the second person, with the reason beside each rule; the Gardener it asks for speaks in the first (`design/brand.md`). In order: what Eden is; the enabled domains, each as `Name (id): what it holds`, since the owner says Hearth and the tools and rows say `kitchen` (the lines are `DOMAIN_BLURBS` in `tools.ts`, one per declared domain, which a test holds to); the voice; what the newest message opens with: the few rows sent whole, the index, that `read-rows` is called before answering about a type's rows or using a row's id, what the index counts for tasks and events, and what empty and locked mean; how rows are written, as JSON lines or as a table; the untrusted rule; that the scrub's `[email]`, `[phone]` and `[number]` are deliberate; how a tool call looks to the owner (a card, a draft that is not saved until kept, a confirm, a decline that is an answer, an error to fix or to report); the grade and that it is the owner's to change; and Markdown, for a reply read in the panel. It never lists the tools: the request's tool list is the one list. A request with no tools is told nothing about them.

It is one system block, cached, and the same for every request at a grade, a model, a language and a set of domains, whatever panel sends it (D-147). What changes rides at the head of the newest message instead (`volatile`): the clock as the owner reads it (`Now: Wednesday 2026-09-30, 09:40 (America/Chicago)`: the weekday, the day and the time in their zone, never a UTC instant the model would have to convert), the domain the panel was opened from, and a line when the thread was trimmed. A tool's own request, which has no index, is told there what it can see, with the locked and the trimmed ids.

`request.snapshot.test.ts` renders the whole prompt, and the head of the message after it, for a fixture pack to `__snapshots__/system-prompt.chat.txt`, a delegated request's to `system-prompt.delegated.txt` and a research request's to `system-prompt.research.txt`, so the words a request carries are a file to read and a change to them is a diff.

### A delegated request

A model-backed tool's request is not a conversation, so it does not get the chat's prompt. `persona()` in `mode: 'delegated'` says it is one job inside Eden whose reply a program reads, asks for the job and nothing around it, names the owner's language for any prose, and keeps the domains, the context frame, the untrusted rule and the scrub line. It has no voice rules, no tools paragraph and no grade.

A handler that parses JSON gives its delegate a `schema`, built with `answer` (`@eden/shared/gardener`): every object closed and every field required, so a field with nothing to say is an empty string, a zero or an empty list, and the parser drops those. The schema's field descriptions carry what the old "Answer as {…}" lines did, and the prompt is left to say what the job is for: use what expires soonest so less is wasted, keep an event evening light. `parseJson` still reads the answer, so a provider without structured output degrades to the old behaviour. A delegate with no schema answers in prose (`brainstorm`).

Before a request is made a delegate's `check` may refuse the input. After it, an answer cut short at `max_tokens`, one the owner stopped, and one that is not the JSON asked for are each an error result with no card: half an answer is never drafted.

No substrate tool is a delegate (D-125): `agenda`, which gathers a day across domains, answers data and the conversation's own model writes the words ("Tools", below).

### A research request

A delegate with `research` (`Research` in `shell/gardener/types.ts`: `maxUses`, `prompt(input, ctx)`, an optional `location(input, ctx)`) is a searching tool, and its tool declares `needs: ["search"]` (D-132). Web search always cites and structured output does not go with citations, so it is two requests. `#research` in `runtime.svelte.ts` makes the first:

- **The request.** The pack is the tool's declared reads with the research prompt as the message, in `mode: 'research'`: `persona()` asks for notes a second request will read, only what the results say, each address exactly as returned. No schema. `tools` is the provider's search tool alone, from `serverTools.search` of the provider's row (`web_search_20250305` for Anthropic), with `max_uses` and, when `location` answers, `user_location` as `approximate` with a city, a region and a timezone, never a coordinate. Its output is capped at 3,072 tokens, plus the thinking room.
- **One budget check and one confirm** cover both requests: the estimate is this request with every search it may make plus the reading request with an allowance for the notes ("Budgets and estimates"). The reading request is then not checked again and its entry records the confirm.
- **What comes back.** The text is the notes; the `server_block` events are the calls and what each returned. The handler's `prompt` and `parse` get both as `ctx.research` (`notes`, `sources`: every address and title the searches returned). The handler wraps the notes with `untrusted(...)` and holds every address in the answer to `sources`, whole (`engineering/meadow.md`, "Discovery").
- **Failures.** An error with status 400 or 403 is `search-refused`; any other error is `network`; a refusal and a stop are what they are for any delegated request; no notes, or no search result, is `search-failed`, with the search's error code when it gave one. Nothing reads `pause_turn`: a paused turn with nothing written is `search-failed`, and one with notes and results is read as it stands.

`suggest-places` and `suggest-listings` are the two that search. Handoffs:

- Each provider maps `search` to its own server tool in `serverTools`; a provider with none cannot run a tool that needs it, and `previewDirect` answers `unavailable`. `serverTools` is the seed's and no owner edit reaches it.
- Never run against the provider: that the request is accepted, that the light model takes the search (the development clamp runs everything on it; if it does not, take `search` off its flags and the resolver moves up a grade and confirms), and `pause_turn` on a long search.
- Hearth's "searching the web" (D-108) is now a tool that declares `needs: ["search"]` and a `research` step.

### Handoffs from the input-cost work

- **Never run live.** None of D-147 to D-151 has been sent to the provider. The first live check: a message that takes two tool rounds, then a follow-up inside five minutes; in the audit log the second round and the follow-up should show cache-read tokens far above input tokens, and the Usage tab's cached share should rise. The development clamp runs the light model, whose smallest cacheable prefix is 4,096 tokens; the tool list alone clears it.
- **The one-hour cache, or a keep-alive.** A gap over five minutes between messages rewrites the whole prefix. Once the Usage tab shows how long the gaps are, either ask for `ttl: '1h'` on the system block and the settled history (a write then costs twice the input price, see "Budgets and estimates") or leave it.
- **Tool search (D-150).** When the list passes roughly 60 tools or 20,000 tokens, mark the domains' tools `defer_loading` and keep the substrate's and the panel's domain loaded; the API then loads definitions on demand without changing the cached prefix.
- **Counts, search and paging in the data layer.** The index loads every row in reach to count it, as the pack always did, and `read-rows` can only answer a whole type, named ids, or names. A count query would make the index cheap; a text filter and a page would let `read-rows` answer "the recipes with lentils".
- **The table against real tokens.** D-151's saving is measured in characters on fixture rows. Run a real pack and a real `read-rows` result through the provider's token count, as lines and as the table, and set `tokensOf`'s divisor from it.
- **The other read tools' results** (`forecast`, `find-similar`, `what-you-know-about-me`, `usage-summary`) are still JSON. `writeRows` would take their lists if they prove a material share of a thread.
- **Trimming the tool descriptions.** The schemas are JSON by the API's contract; the descriptions are the only slack, and after D-147 they are read from the cache.
- **`read-rows` on the Tools page** reads "nothing", since it declares no read of its own; `ToolAbout` could say "whatever the other tools read".
## The scrub

`scrub(text)` replaces emails, phone numbers and account-like numbers (eight or more digits, spaces or dashes between groups) with `[email]`, `[phone]` and `[number]`, leaves dates, times, ULIDs and stamps alone, and is idempotent (D-26). It runs on every row string, on the owner's message and on each turn of the thread, never on the system prompt.

## Tools

`toolIndex(declarations)` is the substrate's tools declared in code (`SUBSTRATE_TOOLS`: `draft-tasks`, `update-tasks`, `agenda`, `what-you-know-about-me`, `usage-summary`, `log-quick`, `propose-fact`, `forget-fact`, `read-page`, `read-rows`; none is model-backed) and every enabled domain's tools from its manifest, each joined to its input schema and description. Anthropic's tool names take no dot, so a domain tool is `<domain>_<id>` on the wire; overrides stay `<domain>.<tool>` and grants stay bare tool ids. Schemas carry `additionalProperties: false` on every object and no numeric or string constraints; the tools that write or draft are marked `strict` (the API holds their input to the schema) and the read tools are not. A request carries the whole index, and the API has two budgets for its strict tools: twenty of them at most (`STRICT_LIMIT`), and twenty-four optional parameters across them, counted through nested objects and list items (`OPTIONAL_LIMIT`). So a domain that changes many things does it with a few batch tools, as Hearth does (D-108): one tool per kind of row, with lists to add, change and remove. A batch tool's rows are mostly fields the model leaves out, which the second budget cannot hold, so the nine named in `LOOSE` (the substrate's `draft-tasks` and `update-tasks`, Hearth's `add-stock`, `update-stock`, `edit-grocery`, `edit-stores`, `save-recipe`, `change-recipe`, and Meadow's `update-places`, D-154) write or draft and are not strict. Eleven are strict (the substrate's `log-quick`, `propose-fact` and `forget-fact`, Hearth's four, Toolbench's two, Meadow's `import-places` and `add-to-calendar`, which add no optional parameter) with fifteen optional parameters between them. A loose tool's handler owns its input checking: it reads each field by type, takes a `null` as a field left out, ignores a key it does not know, and answers "Nothing was changed" for what it cannot read; a new tool with more than a few optional fields joins `LOOSE` on those terms. `validateTools` refuses a read outside the registry, a T3 read, a duplicate or malformed wire name, a schema the API would not take, and more strict tools or more optional parameters across them than the API takes, and the test runs it over the manifests.

A description is the tool's whole contract with the model, which sees nothing else of it, so each one says what the tool does, what comes back, when to use it and what it cannot do; every parameter has its own line. Two are built from data, so they cannot drift from it. `log-quick` takes one `action`, an enum of `<domain>.<action>`, narrowed by `toolIndex` to the quick actions of the domains it is given that `QUICK_ACTION_WORDS` has a line for (what the action does, what its `value` is); with none, the tool is left out. Hearth's `add-to-grocery` has no line, since `edit-grocery` does it with a brand, a size and a store (D-124), so a workspace with Hearth alone has no `log-quick`. `propose-fact` takes a `type` from `PROPOSABLE_FACTS` (the live fact types the substrate does not derive) and its description lists the shape of each type's value, written from `FACT_SHAPES`. `__snapshots__/tools.txt` is every tool as the API is given it.

What a tool answers is written for the model too. A result is plain fields, with a `note` where the next step is not obvious: a drafting tool answers `status: 'drafted'` and that nothing is saved until the owner keeps the card. An error says what was wrong and what to pass instead (an unknown id names the id and where ids come from; a day the forecast does not reach names the days it holds), and nothing falls back silently to a default the model did not ask for. A decline is `cancelled` with words that say not to retry. Every result passes the scrub before it is sent. A delegate's `check` refuses an input it cannot work on (an id that does not resolve, neither of two ids) before a model is resolved, so no request is spent on it.

Handlers are written once, in shared, for both apps (D-157). `DomainLogic.tools` (a domain's `logic.ts`) maps a tool id to a handler, `run(input, ctx)` for a plain or write tool and `delegate` (a prompt, a parser, a card) for a model-backed one. A `run` handler may give a `preview(input)`: what the call would do in the owner's words, one line per change with each row named by its name, which the tool card shows in place of the raw input while it waits on the confirm (the input names rows by id, which says nothing to the owner about a delete). It may also give `asks(input, ctx)`, which makes this one call wait on the owner whatever the tool's grant ("The loop", step 5). What a batch handler reads its input with (`entries`, `ids`, `given`, `together`, `unknown`, `preview`, `withFields`) is `shell/gardener/batch.ts`, shared by the substrate's task tools and Hearth's. A delegate that reads files names them with `Delegate.files` (`capture-haul`, `import-recipe`), which replaces the single image a delegate once carried: the pack's own attachment handling builds the content blocks ("Attachments", below), and a delegate that names files and is given none is not run and answers `no-files`, unless `filesOptional` allows it (a recipe pasted as text). The files a tool may read arrive as `ToolContext.files`: in a conversation the ones on the owner's message, else on the latest earlier message that had any; for a tool a page runs, the ones the page staged. A tool takes no attachment id as input, because the model cannot name an attachment. `ToolContext.links` is the `https` addresses the owner wrote in the conversation's own messages (`linksOf`), which is what `read-page` reads without asking. A result that answers nothing carries `ToolResult.failure` ("A tool run from a page"). `DomainLogic.quickActionHandlers` maps a quick action id to its store write, which `log-quick` dispatches to and the Quick Log sheet (#27) reuses. The substrate's handlers live in `shell/gardener/substrate-tools.ts`. A declared tool with no handler answers "unavailable", and the shell logs the list of them when it starts (`missingHandlers`). The page at `/gardener/tools` lists the index for the owner: one row per tool with its owner, access, grade and the count of ids it may read, the substrate's first; a row unfolds beneath itself (`DataTable`'s `detail`) to `ToolAbout` (`shell/gardener/ToolAbout.svelte`: the description, then access, grade, whether it asks first and the reads by name), the same body the conversation's tool popover shows, with the input schema folded beside it and a warning row for a tool without a handler. The Gardener tab and the panel's header link to it. A domain's `tools.ts` imports only its own store and the shell, as the isolation lint requires.

### The substrate's tools

All ten run in `shell/gardener/substrate-tools.ts`, and none makes a model request.

- **`draft-tasks`** (D-124) takes every task in one call. A row with `repeat` (`every` day, week, month or year, an `interval`, `weekdays`) is a routine, which starts on its `due` or today (`repeatOf`); one with `timesPer` is a habit; never both. It answers each draft's kind and leaves the card.
- **`update-tasks`** (D-124) edits (`changes`: title, `due`, `timeOfDay`, priority, notes), finishes (`done`), reopens, skips and deletes. Every id is checked first, and so is every field: an id named twice, a `due` on a routine or a habit, a `skip` of what is no routine and a `reopen` of a habit are errors that change nothing. `done` is `tasks.complete` for a todo, a checklist and a routine's occurrence today, and `tasks.tally` for a habit. The writes go through the Today store in the order edits, done, reopen, skip, delete (a delete's way back restores the list as it stood, so it is last), with one undo for the call. An edit is `edited` in `@eden/shared/tasks`: a todo's new day keeps its time and a new time keeps its day; a routine's time is its own field.
- **`agenda`** (D-125) answers `agenda(...)` from `@eden/shared/gardener`, pure and tested in Node: per day the events in time order, the tasks due, the routines that fall on it with their state, the tasks done and Sky's reading; when the days reach today, `overdue` (due before the first day asked for), `habits` and `alerts`. A day is the owner's: a due, a completion and an event are placed by `dateIn(zone, …)`, never by the date an instant's text begins with. The handler asks the events for `agendaWindow(first, days)`, a day wider on each side as bare dates, because both stores compare `startAt` as text and a bare date sorts before every instant of that date; the function keeps what falls on the owner's days. Event kinds are gated as the pack gates them (T2 under a grant, T3 never). A calendar that cannot be read is said in a `note`, never passed off as an empty one.
- **`propose-fact`** and **`forget-fact`** (D-127). A proposal may carry `until` and `replaces`; it checks that the replaced fact exists, is shared, is of the same type and is not `system-derived`, and keeps its value on the proposal (`replaced`) so the card reads after the row is gone. `forget-fact` answers a fact that is not shared as one that is not there. `what-you-know-about-me` answers each fact's `id`.
- **`read-page`** (D-126) resolves the address against `ctx.links` (`resolveLink`: the whole address, or the same once scrubbed, since the model was given the owner's words with long numbers cut out), fetches it with `fetchPage`, and answers `page`: the title and the text (`htmlToText`, `pageTitle` in `@eden/shared/api`), cut to 20,000 characters and wrapped by `untrusted(...)` inside the string. Its `preview` is the address in full as `new URL` writes it, so a lookalike host shows as punycode. A `web:*` refusal is put into words the model can pass on; fewer than forty characters of text is a page that says nothing.
- **`read-rows`** (D-148) answers `readRows(...)` from `@eden/shared/gardener`: the rows of one registry id the conversation may read, or the ones named by `ids`, as text in the pack's own format. It declares no read of its own: its reach is the union of what the other tools declared (`ctx.reach`), so it exposes nothing a conversation could not already be sent. Its result carries `reads`, `grants` and `tier`, which the loop puts on the audit entry, the thread and the reply's eye. A row's name, where only names are answered, is the domain's `labels` binding first.

**The tool list stays whole and fixed (D-150).** Every request carries every tool, in one order. Narrowing the list by panel or by message would change the request's first bytes and cost the cache more than the definitions cost to read from it. See the handoff below for when that stops being true.

Handoffs:

- `kitchen_import-recipe` fetches a `url` the model passes with no confirm and outside the link rule: it predates D-126. Its delegate has no `asks`; give delegates one, or check the address against `ctx.links` in its `check`.
- Only an address in the owner's own messages is theirs. One kept on a row they made (a recipe's source, a store's site) still waits on the confirm; widening `linksOf` to those rows needs the row's provenance.
- A page's text is replayed whole only from the last reply (`REPLAY_LIMIT`), so a follow-up two turns later reads the page again, and an address the owner did not give confirms again.
- The guard counts a conversation as holding a page for good. Nothing lifts it, and nothing tells the owner why a write that used to run at once now asks; a line on the card would.
- A thread written before D-124 and D-125 replays calls to `create-task`, `complete-task` and `summarize-day`, names the request's tools no longer hold. It was never run against the provider; a domain switched off already leaves a thread in the same state.
- `ToolAbout` and the Tools page say "Asks first: No" for `read-page`, which asks for some addresses, and nothing says `update-tasks` asks once and then stands.
- `agenda` does not expand an event's `recurrence`, treats an all-day `endAt` as its last day, and does not mark a mirrored event as untrusted: all three are Almanac's (`product/domains/calendar.md`). A birthday is an Event of kind `birthday` once People is built, so it reaches `agenda` through the day's events; the row should then say whose it is (`product/domains/people.md`).
- A reply could link a row as `eden://type/id` and the panel open it, which would do what a navigation tool would without a tool round. `Markdown` draws no such link today.
- Nothing searches past conversations, by design: it would be the free-text memory `product/substrate/profile.md` rules out.

## Attachments

The owner's files on a message (D-82 to D-84). `packages/shared/src/gardener/attachment-limits.ts` is the one place the numbers live: what is accepted (`ACCEPT`, MIME types and the extensions beside them, since an engine leaves `type` empty for `.md`), ten files a message, the size each type may be as stored, the edge and weight an image is sent at, 20 MB a request as sent, and the paste threshold.

**In.** The panel is wrapped in the kit's `Dropzone`, off while the thread list is up or nothing can be asked; the composer's foot has a `FileButton`; the `Composer` hands pasted files and long pastes to `onfiles`. The phone's sheet has no drop zone: its `FileButton` has no `capture`, so the system's chooser offers the camera, the library and files, and a paste works as on desktop (D-163). The staged files are the session's (`chat.staged`), so both surfaces stage alike. All three go through one check (`checkStaged` in `shell/gardener/files.ts`: the kit's `checkFiles`, then each type's own cap and that the file has bytes), and a refusal is one toast in the app's words. A staged file is a `FileChip` above the message, measured while it waits (`measure`: `createImageBitmap` and an `OffscreenCanvas`, written when the CSP had no `blob:`, which `img-src` now has, D-131; a 256 px JPEG thumbnail as a data URL). The send waits for the measuring.

**Stored.** `runtime.ask(text, staged)` writes the files first (`storeFiles`: `attachBytes` each, `photo` or `document`, `part-of` the thread, `captured` holding the pixels; all or none) and then appends the owner's message as `[...attachment blocks, text?]`. An `attachment` block is `{ id, name, mime, size, hash, width?, height? }`. `ask` answers false when nothing was sent, and the panel puts the words and the files back. `MessageBlocks` draws the blocks as chips in the owner's bubble, the thumbnail from the row (`threadAttachments`), `missing` when the row is gone. `segmentsOf` skips the block.

**Sent.** `buildPack` takes the message's files as `attachments` and finds the earlier ones in the thread. A file is a placeholder part of its turn, counted by what its block says (`attachmentTokens`: an image by its sent pixels over 750, text by its bytes over four, a PDF by its bytes over forty with a floor; `sentBytes`), so trimming needs no bytes. Past 20 MB as sent, and then past the budget once the entity rows are gone, the earlier turns' files become `[attachment no longer sent: name]`, the oldest turn's first; then whole exchanges go as before. Only then does `PackReaders.attachment` read what is left (`readForPack`: `readAttachment`, an image over the sent size scaled to a JPEG, kept in memory for the next turn). An image is an `image` block, a PDF a `document` block, a text file `<file name="…">` with its text scrubbed, and a file whose bytes are gone `[attachment unavailable: name]`. The message's files come after the context and before its words; a message of files alone sends no text block. `pack.attachments` is what the audit entry keeps, `pack.attached` the names the "can see" block lists, and a `document` raises the tier to T2.

**Asked.** A request with an image or a PDF in it, the message's or an earlier turn's, resolves its grade with `vision` beside `tools`. A `document` in the pack records a per-request grant on `document` (origin `confirm`), whose id joins the entry's grants. A delegated request that carries files (`capture-haul`, `import-recipe`) counts them in its estimate and records the same grant, in a conversation or run from a page; its audit entry lists them under `attachments`.

Handoffs:

- `capture-haul` asks the model for a box around each item it sees, for the item's picture (D-90). How well the light grade draws one has not been seen live; a box that shows nothing, or most of the photo, is dropped in `haulRows`, and the per-tool override (D-74) is the first thing to try if the pictures are loose.
- In a conversation `capture-haul` and `import-recipe` send their images twice: once in the chat request, as the message's files, and once in the delegated one. The delegated request is the one that reads them; the chat request could carry placeholders for a message whose files a tool will read.
- A draft settled after the owner switched threads may stay pending: `threads.patch` reaches only the open thread or one that is held, and a capture or a recipe draft is settled from the domain's surface, which may be long after its card was pressed.
- Nothing removes an attachment's file: a deleted thread tombstones its attachment rows and the bytes stay in `attachments/`. A sweep of files whose rows have been tombstones past the undo window belongs with the data layer.
- Sync does not carry attachment bytes. On another device a message's files read as `missing` and the model is told they are unavailable; the bytes should cross as encrypted blobs (D-21).
- A chip in a sent message does not open its file: there is no asset protocol, and the chips predate `blob:` in the CSP's `img-src` (D-131). Thumbnails are the data URLs `measure` makes, in the panel and in Hearth's capture sheet alike; opening the stored file itself wants one decision on how it is shown.
- The estimates are heuristics; the provider's token-counting endpoint would make the budget check exact, PDFs most of all.
- A HEIC or TIFF dropped or pasted on the composer is refused by type. Hearth's capture redraws a HEIC as a JPEG itself before anything else (`domains/kitchen/staging.svelte.ts`); the composer could do the same on the way in, which would take what macOS copies from some apps. That redraw relies on the webview decoding HEIC, which is assumed and not verified in the Tauri app.
- The API's own limits (per-image bytes and pixels, request size, PDF pages per model) were taken from memory when the caps were chosen, not checked against the current reference; the caps sit well under them, and should be read against it before they are raised.
- Not verified in the running app: the raw-body `attach_bytes` call with a large file, `dragDropEnabled` reaching the window through each config overlay, whether WKWebView tells a drag's types before the drop (the overlay falls back to the count), and what the clipboard gives for an image copied in Finder.

## Budgets and estimates

The policy row holds the monthly cap (10 USD by default) and the per-request token cap (the model's context when unset). An estimate before sending assumes the pack's tokens in and `maxTokens` out at the resolved model's pricing row; the entry after records the usage the provider reported. A web search has a fee of its own (D-132): `Pricing.search`, in dollars for the one search and not per million, 0.01 in the seed and nothing where a row names none. `estimateCost` adds it for each of the usage's `searches`; `estimateBefore(input, maxTokens, pricing, searches)` adds every search the request may make and `SEARCH_RESULT_TOKENS` (6,000) of input for each, and a searching tool's estimate adds the reading request with 2,500 tokens allowed for the notes. The fee is part of the entry's `costUsd`, so the cap, the Usage tab and `usage-summary` count it with no column of its own. The provider counts the input in three parts and each has its price (`estimateCost`): what it neither read from its cache nor wrote to it at the input price, what it read at `cacheRead`, and what it wrote at `cacheWritePrice`, which is the pricing row's own `cacheWrite` or, where the row names none, a quarter over its input price (D-116). The seed names none, so an input price the owner edits carries the write price with it. The quarter is the provider's five-minute rate, the only kind of cache write the pack asks for (`cache_control` with no `ttl`). This month's spend, which the budget stops on, is the sum of the audit's `costUsd` since the first of the month in the owner's zone.

Handoffs:

- `estimateBefore` assumes nothing is read from the cache, so a follow-up's estimate is an upper bound, and it counts no tool definitions at all (it never did). `tokensOf` is still `chars / 4`: the divisor was to be set from the provider's token count of a real pack, which has not been taken (D-151).
- If the pack ever asks for the one-hour cache (`ttl: '1h'`), a write costs twice the input price, not a quarter over: the price must then follow the TTL of the block written, which one `cacheWrite` per row cannot say.
- There is no interface for editing a pricing row; `ProviderEdits` in the policy row is the only way in. An entry is costed once, from the row as it stood when the request ended, and an entry from before migration 8 stays low by its cache writes.
- No figure has been held against a provider's invoice. The two search allowances are round figures, unmeasured: correct them after the first live searches.

## The audit log

An entry's `attachments` (migration 7) lists the owner's files the request carried, each by hash, type, size and an image's pixels (D-83). `audit_entries` is this device's: 90 days, never exported, never synced, never cleared by a replace, swept when the workspace opens. An entry is written once its request has ended; one the app closed on is written at the next start with the outcome `interrupted` ("A request that never settled"). An entry holds what `product/substrate/ai.md` lists; `reads` carries the row ids read, the ones sent up front and the ones the request's tools fetched (D-148), each id once, which is what "used by N requests" on the profile counts (`audit_usage`). An entry's `cacheWrite` (migration 8) is the input the provider wrote to its cache (D-116). A searching tool leaves two entries (D-132), the research request's and the reading one's, both of the tool's kind (`tool` in a conversation, `page` when a page ran it); the research entry's `tools` lists `web_search` once for each search the provider ran, and its cost holds their fees.

The log is read a page at a time (D-114). `query_audit_page` takes what to keep (a thread, a stretch of `at`, kinds of request, tools as `<domain or substrate>.<id>`, grades, models, outcomes, a row id some read holds), the column to sort by and which way, a limit (fifty; two hundred at most) and an offset, and answers the rows with how many the filters keep in all. The column is one of an enum's, matched to SQL in the crate, never a caller's word; equals fall the latest first. A request's kind is told from its surface and its caller: `conversation` (any surface but `delegated`), `tool` (`delegated` with a `parentRequestId`), `page` (`delegated` without, D-86). `audit_facets` lists the models and tools the log holds, for the filters to offer, and `audit_thread_totals` what each conversation's requests came to. `query_audit` stays for what reads the whole log. The browser's engine answers all of them from the same pure functions (`audit-page.ts`), whose tests use the entries of the crate's own.

The Audit log tab (`page/AuditTab.svelte`) holds no state of its own: `parseAuditParams` reads the filters, the sort and the page from the address (`/gardener/audit?thread=…&kind=tool,page&range=7d&sort=cost&dir=asc&page=2`, `fact=<row id>` for the requests that read one row), `auditQueryOf` turns them into the query, and every change is a `goto` to the next address (`gotoAudit`), a step the back arrow undoes. A word the log does not know is dropped. The time filter is a preset (today, seven days, thirty, this month), counted in the owner's zone. A row unfolds beneath itself to its reads, tools, grants and thread; "Open the calling request" shows only while that request is on the page. The Gardener tab and the profile page link to the tab.

Handoffs:

- `fact=` has a reader and no writer: the profile's "used by N requests" still opens the whole log, and the reply's eye links nowhere (`product/substrate/ai.md`, "Audit log").
- A filter that takes several values takes one pick per opening, since the kit's `Menu` closes on a pick. A range of dates the owner types, and a filter by domain, are not built.
- The calling request of a tool run is reachable only when it is on the same page; nothing fetches one entry by id for the page.
- The search count is in an entry's `tools`, not a column, and `usage_days` does not hold it: a migration 10 on `audit_entries` and `usage_days` would make it one, and the Usage tab could then say searches beside tokens.

## Usage

`usage_days` (migration 9, `usage.rs`) is what the audit entries came to, a day at a time, kept for good (D-115). `audit::record` adds the entry it has just written to its day in the same transaction: one row per day, provider, model, grade, kind, domain and tool, with `''` where the entry had no grade, domain or tool, and the requests, tokens and dollars summed. `declined` and `budget` entries never left the device and are not added. The day is `AuditEntryInput.day`, which the runtime sets to the owner's local day of the entry's `at` (`dated` in `runtime.svelte.ts`, the zone the budget's month uses); an entry without one takes the device's day. The sweep never touches the table, a replace never clears it, and no bundle holds it (`the_audit_never_leaves`). The migration summed in the entries the log already held, by the device's day (SQLite's `localtime`).

`query_usage` takes a first and a last day and what to group by: one span of time (`day`, `week` as its Monday, `month`, `year`) as the bucket, and any of provider, model, grade, kind, domain and tool. Nothing to group by is one row of totals; nothing recorded is no row. `usage.ts` holds the same rules for the browser's engine and for the page: `kindOf`, `addUsage`, `usageOf`, `bucketsBetween`, `rangeStart`.

The Usage tab (`page/UsageTab.svelte`) reads every day's rows once and sums them itself: this month against the cap, the last thirty days, all time and the month's requests; the spend as the kit's `BarChart` stacked by grade, by day (thirty days), week (twelve), month (twelve) or year (all there is); and where it went over that stretch by model, by grade and by what ran. It reads again when a request is audited. Its composition is mocked in Storybook (Domains/Gardener/Usage, D-54).

The Gardener reads the rollup too, through the substrate's `usage-summary` (D-121): a plain read tool that takes a first and a last day and what to group by, as `query_usage` does, and answers the rows with the fields not grouped by left out, today's date, the monthly cap and the month's spend, and a note that the figures are estimates. It declares no reads, since the rollup is no registry resource, so it adds nothing to the pack or to what the "can see" chip lists. Its handler (`substrate-tools.ts`) refuses a day that is not a day, a group it does not know and two spans of time in words the model can act on, and answers two hundred rows at most, saying so when there were more. Nothing of the audit log is in its reach, and no tool writes the rollup.

Handoffs:

- `usage-summary` was never run by a live model: its handler was called by hand in the browser build. What a conversation cost is not in its reach; `audit_thread_totals` behind a second read tool, or the thread in the rollup's key (below), would give it. A tile on the Garden for the month's spend is a tile of the shell's (`shell.json`), not this tool's.
- A conversation's total (`audit_thread_totals`, the Conversations tab) comes from the log, so it covers ninety days. A total that lasts needs the thread in the rollup's key, which grows a row per conversation per day.
- The chart leaves out spend with no grade (none is written today); the By grade table names it. A bar under the pointer is read out by the kit (D-117), named by its short label (the day and month, the month, the year); the readout has no keyboard way in.
- The Usage tab reads the whole rollup at once. Years on, read the range the span shows instead (`fromDay`).
- The migration's backfill and `localtime` were run in tests only, never against the owner's workspace in the installed app, and never on iOS or Android.

## The Gardener's page

`/gardener/[[tab]]` (D-113) is the shell's own page: `page/Gardener.svelte` draws the header and a `Segmented` of the four tabs, the tab in the address as a domain's is (`engineering/app-scaffold.md`), Usage when none is named. The sidebar's entry is the pinned one of `shell.json` given an `href` by the desktop layout (`places` in `routes/+layout.svelte`), which makes it a link and the current item on the page; ⌘G and the status bar's chip still toggle the panel. `routes/+page.ts` knows the page as a place a launch may return to. The Conversations tab lists every thread with its totals; opening one opens the panel on it.

The phone mounts the same page at the same route, reached from More, where the Gardener's pinned entry is a place (`place: true` in `shell.json`), and a conversation opens in the chat sheet (D-164). The tabs are named without their icons there; the audit log's `DataTable` keeps when, tool, cost and outcome and the tools list keeps the tool and its access, each by its place in the full column list, and the rest is in the row's detail.

Handoffs:

## Threads and policy

`threads` and `messages` are rows of the workspace: stamped, tombstoned, exported in the full bundle and merged by stamp. A message's `blocks` is JSON the frontend shapes, as a fact's value is: text, tool cards with their state (`pending`, `running`, `done`, `failed`, `cancelled`), proposal and draft cards, the can-see snapshot, an error, and the `writing` mark of a reply whose request has not ended. A card stored `running` or `pending` by a request that is no longer live reads as cancelled. The blocks are stored in the order they happened and drawn in it: `segmentsOf` (`packages/shared/src/gardener/segments.ts`) turns them into text, single cards and runs (two or more consecutive `read` calls that are running, done or cancelled), and the panel draws a run as the kit's `ToolRun`; the mobile chat (#19) draws from the same function and the same component. A reply's text is Markdown: the chat's persona asks for it (`markdown` on the pack request; a delegated request leaves it off, since a handler parses its answer) and the panel draws it with the kit's `Markdown`, which never injects HTML. A message's foot shows its `createdAt`, so a reply's "Received at" is when it began. A thread's tier is the highest tier it read; a T2 thread shows the lock and stays out of future packs unless the owner includes it, which records a per-request grant on the T2 id that made it so.

`policy` is a generic key-value table of workspace policy (D-37). The row `gardener` holds the owner's sparse edits over the seed, the overrides, and the two caps. The conversation's grade is a per-device setting.

## The development clamp

In `development` (`yarn dev`) and in the browser (`web`) the light and the standard grade resolve to the seed's light model and the deep grade to its standard one (D-81); every override is left out, and the deep model is never reached. So developing spends little by default, and the standard model, which reasons where the light one does not, is one switch of the chip away. Staging and production use the real map. The audit entry records the model that ran. A `deep` tool still confirms under the clamp, since the confirm is about the tool's cost class; the sheet shows the standard model and its estimate, and the Gardener tab says the clamp is on and names both models, as does the info button just left of the status bar's grade switch (the kit's `StatusBarNotice`).

## The browser fallback

`yarn dev:web` has no crate: `hasSecret` is false, `gardenerSend` rejects `unavailable`, and the panel says the Gardener runs in the installed app. Threads, messages, the policy and the audit log work in the engine, so the panel is developed against `FakeTransport`, a scripted stream; a message that names the moon is answered with a line, three `sun-and-moon` calls and an answer, which exercises the order of a reply and the fold. A request held to a schema is answered in that shape (`shell/gardener/transport.ts`): a canned haul for `capture-haul`, a canned recipe for `import-recipe`, candidates, listings and tags for Meadow's three, and for any other schema an answer that is complete and empty. A request that carries a web search is answered with two scripted searches as `server_block` events, notes, and a closing usage with `searches`; the candidates include one no geocoder finds, a website the search did not return and a place with no returned source, so each guard shows. So the capture sheet, the recipe import, Find more, the listings search and the import's tagging can be walked in the browser. `read-page` cannot: `fetchPage` rejects with `web:unavailable` there, which the tool answers in words.
